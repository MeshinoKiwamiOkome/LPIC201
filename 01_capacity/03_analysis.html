① リソース監視ツール一覧

重要ポイント①：監視ツールは「データ収集・蓄積型」と「アラート・監視型」に大別される
collectd・MRTG・Cacti はデータ収集とグラフ化が主目的で、 Nagios・Icinga2 はサービス監視とアラート通知が主目的です。 実際の運用では両方を組み合わせて使います。
collectd
データ収集・蓄積
軽量なシステム統計収集デーモン。プラグイン方式で多様なリソースを収集しRRDtoolやInfluxDBに保存
Nagios
監視・アラート
業界標準のネットワーク・サービス監視ツール。ホスト・サービスの死活監視とアラート通知が中心
MRTG
グラフ生成
Multi Router Traffic Grapher。SNMPでネットワーク機器のトラフィックを収集しHTMLグラフを生成
Cacti
グラフ生成・Web UI
MRTGの後継的存在。RRDtoolをバックエンドにWebUIでグラフを管理。SNMPとカスタムスクリプト対応
Icinga2
監視・アラート
Nagiosのフォーク。分散監視・REST API・モダンなWebUI（Icinga Web 2）を備えた次世代監視ツール

監視ツール比較表

ツール 主な用途 データ収集 グラフ化 アラート WebUI
collectd 統計収集・蓄積 ✅ プラグイン △ 別途必要 △ プラグイン ❌
Nagios 死活監視・アラート ✅ プラグイン △ 別途必要 ✅ ✅ 基本的
MRTG ネットワークグラフ ✅ SNMP ✅ HTML生成 ❌ △ 静的HTML
Cacti グラフ管理・可視化 ✅ SNMP/スクリプト ✅ RRDtool ✅ プラグイン ✅ 高機能
Icinga2 総合監視・アラート ✅ プラグイン ✅ 連携 ✅ ✅ モダン

② 需要の分析と将来予測

重要ポイント②：将来予測は「過去データのトレンド分析」＋「ビジネス計画との照合」で行う
単純な線形外挿だけでなく、季節性・イベント・ビジネス成長率を考慮した予測が重要です。

リソース別：分析と予測のポイント（タブで切り替え）

CPU 需要の分析と予測

分析項目確認方法閾値の目安
ロードアベレージsar -q / uptimeコア数の70%超で要注意・100%超で過負荷
CPU使用率（us）sar -u / top継続80%超で増強検討
iowait（wa）sar -u / vmstat継続20%超でディスクがボトルネック
コア別使用率sar -P ALL / top（1キー）特定コアのみ高い場合はシングルスレッド処理の可能性
✅ CPU予測のポイント
・sar -u の長期データでトレンドを確認（週・月単位）
・ピーク時のロードアベレージがコア数の70%を超えるようになったら増強計画を開始
・アプリケーションのユーザー数増加率とCPU使用率の相関を分析する

メモリ 需要の分析と予測

分析項目確認方法閾値の目安
実メモリ使用量sar -r / free -h（total - buff/cache）が物理メモリの80%超で要注意
スワップ使用量sar -S / vmstat使用量が増加傾向にある場合は要増強
スワップイン・アウトsar -W / vmstat（si/so）継続的に0以外で深刻なメモリ不足
OOMキラー発動dmesg | grep -i oom発動している場合は即時増強が必要
✅ メモリ予測のポイント
・Linuxは空きメモリをキャッシュに積極利用するため、freeの値だけで判断しない
・スワップの使用量が増加傾向にある場合は近い将来メモリ不足になるサイン
・アプリケーションのバージョンアップ・機能追加でメモリ使用量が増加することを考慮する

ディスクI/O 需要の分析と予測

分析項目確認方法閾値の目安
ディスク使用量df -h / du -sh使用率80%超で要注意・90%超で緊急対応
I/Oスループットsar -b / sar -dデバイスの最大スループットの70%超で要注意
I/O待ち時間sar -d（await）/ iotopHDDで20ms超・SSDで5ms超で要注意
inode使用率df -i80%超で要注意（小ファイル多数の場合に枯渇）
✅ ディスク予測のポイント
・ログファイル・データベースの増加率からディスク満杯になる時期を予測する
・df -h を定期的に記録し、使用量の増加トレンドをグラフ化する（Cacti/collectdが有効）
・inode枯渇はディスク空き容量があっても発生するため、df -i も定期確認する

ネットワーク 需要の分析と予測

分析項目確認方法閾値の目安
帯域使用率sar -n DEV / MRTG / Cacti回線帯域の70%超で要注意
パケットエラーsar -n EDEV / ip -s linkエラーが増加傾向にある場合はハード障害の可能性
TCP接続数sar -n TCP / ss -sアプリケーションの最大接続数を超えないよう管理
レイテンシping / traceroute平常時との乖離が大きい場合は経路障害の可能性
✅ ネットワーク予測のポイント
・MRTGやCactiでトラフィックの長期トレンドをグラフ化するのが最も効果的
・ピーク時の帯域使用率が70%を超えたら回線増速・CDN導入・負荷分散を検討
・ユーザー数の増加とトラフィック量の相関を分析し、将来の帯域需要を予測する

④ リソース問題の解決

重要ポイント④：リソース問題の解決は「カーネル」「サービス」「メモリ・スワップ」の3つの観点から行う
ハードウェアを増強する前に、まずソフトウェアレベルのチューニングで解決できないかを検討します。
⚙️ カーネルによる問題解決
  1. カーネルパラメータの確認
    sysctl -a
  2. 一時的な変更（即時反映）
    sysctl -w vm.swappiness=10
  3. 永続的な変更
    /etc/sysctl.conf に記述
    sysctl -p で反映
  4. カーネルバージョン確認
    uname -r
🔧 サービスによる問題解決
  1. リソース消費プロセスの特定
    top / ps aux --sort=-%cpu
  2. 不要なサービスの停止
    systemctl stop サービス名
  3. 自動起動の無効化
    systemctl disable サービス名
  4. サービス設定のチューニング
    （ワーカー数・タイムアウト値など）
  5. 起動サービス一覧の確認
    systemctl list-units --type=service
🧠 メモリとスワップの問題解決
  1. メモリ使用量の確認
    free -h / sar -r
  2. スワップ使用状況の確認
    swapon --show
  3. swappinessの調整
    sysctl vm.swappiness=10
  4. スワップファイルの追加
    fallocate -l 2G /swapfile
    mkswap /swapfile
    swapon /swapfile
  5. OOMキラーの確認
    dmesg | grep -i oom

カーネルパラメータ：主要なチューニング項目

# ===== メモリ・スワップ関連 =====

# vm.swappiness：スワップの積極度（0〜100、デフォルト60）
# 低いほどスワップを使わずRAMを優先する
$ sysctl -w vm.swappiness=10

# vm.dirty_ratio：ダーティページの最大割合（デフォルト20）
# ディスク書き込みのバッファリング量を制御
$ sysctl -w vm.dirty_ratio=15

# vm.overcommit_memory：メモリオーバーコミットの設定
# 0=ヒューリスティック / 1=常に許可 / 2=制限あり
$ sysctl -w vm.overcommit_memory=1

# ===== ネットワーク関連 =====

# net.core.somaxconn：接続キューの最大サイズ（デフォルト128）
$ sysctl -w net.core.somaxconn=1024

# net.ipv4.tcp_fin_timeout：TIME_WAIT状態のタイムアウト（秒）
$ sysctl -w net.ipv4.tcp_fin_timeout=30

# ===== ファイルシステム関連 =====

# fs.file-max：システム全体のファイルディスクリプタ最大数
$ sysctl -w fs.file-max=100000

# 永続化（再起動後も有効）
$ echo "vm.swappiness=10" >> /etc/sysctl.conf
$ sysctl -p   # /etc/sysctl.conf を即時反映

スワップ領域の追加手順

# 現在のスワップ状況を確認
$ swapon --show
NAME      TYPE SIZE USED PRIO
/dev/sda2 partition 2G 68M   -2

# 2GBのスワップファイルを作成
$ sudo fallocate -l 2G /swapfile
$ sudo chmod 600 /swapfile        # root のみ読み書き可能に
$ sudo mkswap /swapfile           # スワップ領域として初期化
$ sudo swapon /swapfile           # スワップを有効化

# 確認
$ swapon --show
NAME      TYPE  SIZE USED PRIO
/dev/sda2 partition 2G  68M  -2
/swapfile file      2G   0B  -3

# 永続化（/etc/fstabに追記）
$ echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

⚠️ 問題解決の優先順位
1. まずソフトウェアチューニング（カーネルパラメータ・不要サービス停止）で改善を試みる
2. 改善しない場合はアプリケーションの最適化（設定・コード改善）を検討
3. それでも不足する場合はハードウェア増強（スケールアップ・スケールアウト）を実施
ハードウェア増強は最終手段であり、根本原因を特定せずに増強しても問題が再発します。
